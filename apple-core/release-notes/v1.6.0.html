Apple Core 1.6.0

Cloud clients can now identify themselves without registering, apps are opened when a request needs them, and a path outside your shared folders no longer tells the caller anything about itself.

Clients identify themselves by URL

Until now a cloud client had to register before it could connect, and it registered again every time it reconnected. The result was a Clients list with several entries of the same name, issued in the same second, only one of which was live.

Apple Core now supports Client ID Metadata Documents, the mechanism Anthropic recommends and which Claude products use. The client's identifier is an https URL serving its own metadata, so it keeps one identity for as long as it keeps that URL, and reconnecting updates the existing entry instead of adding another.

Because the identifier is a URL this server fetches, it is treated as hostile:

  • https only, with no credentials, no fragment, and no dot segments in the path. Identifiers are compared literally, so a port makes a different client.
  • The host must not resolve to a special-use address. This app runs on a home network, and an unguarded fetch of a client-supplied URL would reach the router and everything else on it. Every address a name resolves to is checked, not just the first.
  • Redirects are never followed, at most 5KB is read, and only a 200 counts.
  • The document must claim the identifier it was fetched from. Without that check anyone could point a request at somebody else's document and borrow their name on the consent screen.
  • A document carrying a client secret is refused, since it is a public document.

The consent page now shows the hostname the identifier comes from. A client supplies its own display name, so the name is exactly what an impersonator would get right; the hostname is the part it cannot.

Existing registered clients keep working and are unaffected.

Apps open when a request needs them

Asking about mail while Mail was closed used to fail, or launch the app into your face. Apple Core now opens the app a request depends on, without bringing it to the front, and waits for it to finish launching before running anything. This covers Mail, Notes and Messages, at every point a script runs.

A path outside your shared folders reveals nothing

Asking for a file outside the shared folders could answer "that is a broken symbolic link" or "that does not exist". Both are facts about a file the caller was never allowed to see, which made the filesystem surface usable as a probe for what exists elsewhere on the Mac.

Containment is now decided before anything else, so every path outside your shared folders gets the same answer. The check that refuses a broken symbolic link inside a shared folder is unchanged, and its message no longer talks about writing when you were reading.

When macOS will not show a permission prompt

Some Macs are configured so that macOS refuses to display consent prompts for apps Apple did not sign, which custom boot-args such as amfi_get_out_of_my_way cause. Asking for automation access there came back as "Denied", which looked like a decision somebody had made and sent you to System Settings, where no entry exists because nothing was recorded.

That case is now told apart from a real refusal and explained where it appears, including what causes it. Neither button is offered, because neither would help.

Upgrading

1.0.3 and later update automatically. Installs on 1.0.0 through 1.0.2 still need the one-time manual reinstall described in the 1.0.3 notes, because their update signing key does not match the feed.

No new permissions, and no shared folder or client approval changes. Every Apple Core install uses its own Cloudflare account and its own tunnel; nothing about anyone else's deployment ships in the app.
