Apple Core 1.6.1

Two corrections to 1.6.0, both found by exercising it against a running server.

A rejected client identifier said the wrong thing

A client identifier that Apple Core refuses — a host resolving to a private address, a document claiming a different identifier, a document carrying a secret — came back as 500, "Apple Core could not save the OAuth client registration". Nothing had failed to save, and nothing was wrong on the server: the client's own identifier or document was at fault.

Before 1.6.0 that catch-all was close enough to true, because the only thing that could fail there was writing a registration to disk. Client ID Metadata Documents added a second way to fail and inherited the wrong explanation.

These now return 400 with the actual reason, naming what was rejected and why, so a client that publishes a bad document can see what to fix.

A way out of a blocked permission prompt

Where macOS refuses to show a consent prompt, Apple Core says so, but it only offered "restore the default security settings" — which on a Mac configured that way for a reason reads as a permanent trade-off.

It isn't one. The permission is stored separately from the setting that blocks the prompt, so it only has to be granted once: clear the boot-args, restart, ask again and allow it, then put the boot-args back. The permission stays. The explanation now says that.

Upgrading

1.0.3 and later update automatically. Installs on 1.0.0 through 1.0.2 still need the one-time manual reinstall described in the 1.0.3 notes, because their update signing key does not match the feed.

Nothing to redo, and no new permissions.
